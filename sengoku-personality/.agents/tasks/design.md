# 戦国武将性格診断 ～あなたは戦国時代の誰に似ている？～ 要件定義 + 技術設計書

対象: 大学祭展示用 Web アプリ(`sengoku-personality/`)。**第 3 版(第 2 版への design-review の指摘 12 件を反映した改訂)**。各指摘への対応は末尾「改訂履歴 / レビュー指摘への対応」に記載。
この文書は「要件定義(Part A)」と「技術設計(Part B)」を 1 ファイルにまとめたもの。Part B の数値データ(15問の配点・20人のパラメータ)は、設計時に Node プロトタイプで 10 万通りの乱数回答を流して分布を検証済みの値であり、そのまま `questions.js` / `generals.js` に転記してよい(検証結果は B-19 に記載)。**第 3 版では位置バイアス対策として Q6〜Q15 の選択肢の並び順を入れ替えた(文言と配点の組は第 2 版と同一で、並びだけが違う。20 人のパラメータは不変)。** 実装者は第 2 版の並びではなく本書 B-5 の並びを転記すること。

# Part A. 要件定義

## A-1. Summary

来場者が日常場面の 15 問(各 4 択)に答えると、6 つの性格パラメータ(統率力・行動力・知略・社交性・慎重さ・革新性、各 0〜100)を算出し、20 人の戦国武将との 6 次元ユークリッド距離から最も近い武将を判定する、完全オフライン動作の静的 Web アプリ。結果画面(名前・画像/代替カード・類似度・タイプ・横棒グラフ+レーダーチャート・似ている理由・TOP3・詳細モーダル)、ブラウザ localStorage による「本日の戦国武将ランキング」(日別/累計)、縦長の結果カード画像(PNG)保存を備える。デザインは「戦国 × 和風 × 現代的ゲーム UI」。HTML5 / CSS3 / バニラ JavaScript のみ、ビルド不要、`index.html` をダブルクリック(`file://`)で動くこと。

## A-2. 前提(Assumptions)

- A1. 対象ブラウザは最新の Chrome / Edge / Firefox / Safari(iOS Safari 15.4 以降を含む)。IE は対象外。`<dialog>`、`Canvas 2D`、`localStorage`、CSS Grid/Flex、`prefers-reduced-motion` を使用してよい。
- A2. 展示は主に PC(1280×720 以上)+ マウス、補助としてスマホ縦画面(最小 360×640)。
- A3. 画像素材は著作権・利用条件が確認できないため**同梱しない**。デフォルトは全 20 人ぶんを SVG/CSS で自作する「代替カード(家紋風)」で表示する。PD/CC0 の画像を入手できた場合のみ `assets/images/` に置き `generals.js` の `image` を設定して差し替える(READMEに手順、`assets/images/CREDITS.md` に出典記録)。
- A4. ユーザー側の 6 値は「質問の最小〜最大配点で 0〜100 に正規化」する仕様のため、ランダム回答では各軸の平均 37〜46・標準偏差 約 10 に集中する(数学的な性質。幅 100 を 15 問の独立選択では使い切れない)。そのため武将パラメータは**この到達可能な範囲に収まるよう**設計し(19〜72)、「武将の数値が 100 に届かない」ことを UI 上の注記で補う(例: 信長の革新性 = 67)。スペック例の `innovation: 100` は例示であり固定要件ではないと解釈する。
- A5. 「どんな回答でも特定武将に固定されない」「同じ回答(同じ選択肢位置)を選ぶだけで特定の武将になる」の回避は、(i) 全A/全B/全C/全D の 4 パターンが互いに異なる 1 位を返す(循環パターンは参考出力)、(ii) **一様乱数回答の最多出現が 9% 以下・最少が 1.5% 以上**、(iii) **傾向付き乱数回答の最多が 12% 以下・最少が 0.5% 以上**、(iv) **位置バイアス耐性**: 特定の文字 X(A/B/C/D)を確率 p で選び、それ以外の場面は 4 択から一様ランダムに選ぶ回答集団で、p=0.7 なら 1 位の最多が 25% 以下、p=0.85 なら 40% 以下、いずれも 20 人中 18 人以上が出現する。加えて文字別プロファイル(全X の 6 軸値)の軸ごとの文字間最大差が 15 点以下、で判定する(閾値が 2 種類あるのは、一様乱数は設計目標 2〜9% の劣化検出用、傾向付き乱数は偏った回答集団でも全員が出現することの確認用で、目的が異なるため)。傾向付き乱数の最多 > 11% または最少 < 0.6% は「警告」として出力する(合格だが調整の余裕が薄い)。
- A6. 日付別集計の「日付」は端末のローカル日付(`YYYY-MM-DD`)。
- A7. localStorage は端末+ブラウザ+オリジン単位。`file://` で開く場合と `http://localhost` で開く場合は別オリジン扱いで集計が別になる。展示での**標準の開き方は「Chrome で `index.html` を `file://` で開く(依存ソフトなし)」に確定**する。代替は `python -m http.server 8000` → `http://localhost:8000/`。途中で開き方を切り替えると集計が分かれる(READMEに明記)。要件 §2 の「ローカルサーバーでの動作を基本」は、サーバー経由でも同一コードで動くこと(AC-1 を両方式で確認)で満たし、`file://` を標準にするのは依存ソフトを不要にして展示当日の事故を減らすため。

## A-3. Functional Requirements

- FR-1 スタート画面: タイトル「戦国武将性格診断」(大)、サブタイトル「もしあなたが戦国時代に生まれていたら、どの武将に似ていたのか？」、説明文「15の質問からあなたの性格を分析。織田信長、徳川家康、伊達政宗など、名だたる戦国武将の中から、あなたに最も近い人物を診断します。」、中央の大ボタン「いざ、診断開始！」、城・旗・家紋の装飾(インライン SVG/CSS)、免責の小文字、目立たない「運営用(集計)」入口。
- FR-2 質問: 全 15 問を 1 問ずつ表示。各 4 択(A〜D、固定順)。現在番号「3 / 15」、プログレスバー、大きな選択肢ボタン、「前の質問へ」、回答変更可、全 15 問回答で診断演出へ。サンプル 5 問は指定文言そのまま。
- FR-3 スコア: 状態は `answers[15]`(選択 index 0〜3 または null)のみ保持。スコアは毎回 `answers` から全再計算(二重加算が構造的に起きない)。
- FR-4 6 パラメータ: 各選択肢に 6 軸の加点/減点(負値可)。各軸を「質問データから算出した取りうる最小合計〜最大合計」で 0〜100 に正規化。
- FR-5 武将 20 人(指定 20 名)を `generals.js` に登録。データ形式は指定 + 拡張項目(生没年・活躍地域・主な功績・有名な出来事・診断用性格イメージ・類似理由用テキスト・家紋風シンボル設定)。
- FR-6 診断: 6 次元ユークリッド距離 → 類似度 `round(max(0,min(100,(1-d/maxD)*100)))`、`maxD = sqrt(6*100^2)`。20 人を降順に並べ、同点は(丸め前距離の小さい順 → 武将配列順)で決定論的に確定。同じ回答なら必ず同じ結果(乱数・日時非依存)。
- FR-7 診断演出: 最後の回答の確定から 約 2.7 秒(回答確定の待ち 0.24 秒 + 演出 2.5 秒)、3 段階の文言(「あなたの武将としての資質を分析中……」→「戦国の英傑たちと比較中……」→「あなたの運命の武将は……」)と家紋・和風エフェクト。連打・二重遷移を防止。
- FR-8 結果画面(最重要): 「あなたに最も似ている戦国武将は……」→ 金枠付き画像(発表アニメ)→ 武将名(大)/「類似度 92%」/「〇〇タイプ」→ 横棒グラフ(6 軸)+レーダーチャート(ユーザーと 1 位の重ね描き、ライブラリ不使用の自作 SVG)→「あなたと〇〇が似ている理由」(自動生成文)→ TOP3(名前/画像/類似度、クリックで詳細モーダル)→ 20 人全順位(折りたたみ)→ ボタン「結果を画像で保存」「本日のランキングを見る」「最初に戻る」。
- FR-9 武将詳細モーダル: 名前・生没年・活躍地域・主な功績・有名な出来事・診断用の性格イメージ(+診断用パラメータ)。史実は確立した事実のみ、不確かな逸話は「〜と伝えられる」。
- FR-10 ランキング(localStorage): 結果確定時に 1 位武将を**1 回だけ**加算。「本日の戦国武将ランキング」形式(「1位 織田信長型　25人」)。**本日 / 日付別(保存済みの任意の日付を選択) / 累計**の 3 区分を切り替えられる(複数日開催の 2 日目以降も過去日を閲覧可能)。localStorage 不可でも診断は例外なく動作。運営用リセットは目立たない場所+確認ダイアログ必須。
- FR-11 結果画像保存: Canvas で 1080×1920 の縦長カード PNG を生成しダウンロード(タイトル/武将名/武将画像または代替/類似度/タイプ/6 パラメータ)。`file://` でも必ず成功する(taint 回避+フォールバック)。
- FR-12 画像: 画像未設定または読込失敗時は自動で代替カード。画像ファイルが一つも無くても全機能が動く。
- FR-13 展示運用: 「最初に戻る」で回答・スコア・結果・DOM を完全リセット。回答/結果は localStorage・URL・Cookie に保存しない(保存するのはランキング集計のみ)。無操作で自動的にスタートへ戻る(`app.js` の定数で変更/無効化可)。ブラウザの戻る/リロード/bfcache 復元で壊れない・前の人の結果が残らない。
- FR-14 免責表示: 「エンターテインメント用の診断であり、歴史上の人物の性格を科学的に判定するものではない」「武将の数値は診断用の仮想モデルで歴史学的数値ではない」「類似度は心理学的な確率ではなくアプリ内モデルでの近さ」をスタート/結果画面/README に明記。
- FR-15 テスト用ツール: `tools/simulate.js`(ブラウザ非依存)で分布・決定論・不変条件・妥当性を検証。`tools/check-static.js` で外部通信禁止・ES Modules 禁止などを静的検査。

## A-4. Non-Functional Requirements

- NFR-1 オフライン/外部通信ゼロ: CDN・外部フォント・fetch・XHR・WebSocket・外部画像 URL 禁止。HTML・JS だけでなく **CSS(`@import`、`@font-face` の外部 `url()`、`url(http…)`)も対象**で、`tools/check-static.js` が `index.html`・`js/*.js`・`css/style.css` を機械的に検査する(B-19 #14)。
- NFR-2 `file://` 直開きで動作: ES Modules 不使用、通常の `<script>` のみ、JSON を fetch しない。
- NFR-3 性能: 初回表示 1 秒以内(総 JS+CSS 目安 200KB 未満)。1 診断の計算は 1ms オーダー。結果カード生成は 2 秒以内(目安)。
- NFR-4 操作性: マウスのみで完結。選択肢ボタン高さ 56px 以上(PC 64px 以上)。本文 18px 以上(スマホ 16px 以上)。1 診断 2〜3 分。
- NFR-5 アクセシビリティ: キーボード到達可能、フォーカス表示(3px 金アウトライン)、`aria-*`、本文コントラスト 4.5:1 以上、`prefers-reduced-motion` で装飾アニメ無効化、色だけに依存しない凡例。(WCAG 準拠の完全な検証は支援技術を用いた手動確認と専門家レビューが別途必要。)
- NFR-6 プライバシー: 個人情報入力なし。保存は武将別の件数のみ。
- NFR-7 保守性: 質問データ・武将データ・診断ロジック・表示処理を別ファイルに分離。データのみの変更で分布調整が可能。
- NFR-8 レスポンシブ: 320px〜1920px で水平スクロールなし・レイアウト崩れなし。スマホは縦画面最適化。

## A-5. Acceptance Criteria(番号付き・検証可能)

- AC-1 `index.html` を `file://` で開き、コンソールエラーなしでスタート画面が表示される。
- AC-2 「いざ、診断開始！」で Q1 が表示され、「1 / 15」とプログレスバー(aria-valuenow=1, max=15)が表示される。
- AC-3 質問は 15 問、各 4 択、Q1〜Q5 の文言が本書 B-5 と完全一致する。
- AC-4 選択肢を押すと約 0.25 秒後に次の問へ進み、高速連打しても 1 問しか進まない(1 クリックで 2 問飛ばない)。
- AC-5 Q2 以降で「前の質問へ」を押すと直前の問に戻り、選択済みの選択肢が強調表示される。回答を変更して最後まで進めても、結果は「最初からその回答で答えた場合」と一致する(二重加算なし)。
- AC-6 全 15 問回答後、回答確定の 0.24 秒後に始まる 2.5 秒の演出(3 段階文言。切替は 0 / 約 0.83 / 約 1.67 秒、結果へは 2.5 秒。`CONFIG.ANALYZE_TOTAL_MS` の 1/3 刻み)を挟んで結果画面へ遷移する(回答確定から結果まで約 2.7 秒)。演出中のクリック/連打で二重遷移・二重カウントしない。
- AC-7 結果画面に、武将名・類似度(整数%)・「〇〇タイプ」・金枠付き画像(代替カード)・6 軸の横棒グラフ・レーダーチャート(ユーザー+1 位武将の 2 系列と凡例)・理由文・TOP3・20 人折りたたみ一覧が表示される。
- AC-8 表示される TOP3 と 20 人一覧の並びは `Diagnosis.diagnose()` の順位と完全一致し、類似度は降順(同値は許容)。
- AC-9 `Diagnosis.diagnose(answers)` は同じ `answers` で何度呼んでも(別プロセスでも)JSON 文字列として完全に同一の結果を返す。
- AC-10 正規化後の 6 値は常に 0 以上 100 以下。類似度は 0 以上 100 以下の整数。
- AC-11 `node tools/simulate.js` で、固定シードのランダム回答 100,000 通りにおいて 20 人全員が出現し、(a) 一様乱数: 最多 ≤ 9% かつ 最少 ≥ 1.5%、(b) 傾向付き乱数: 最多 ≤ 12% かつ 最少 ≥ 0.5%(現行データの実測は B-19: 一様乱数で 2.5%〜6.3%、傾向付きで 0.75%〜8.6%)。(b) の最多 > 11% または最少 < 0.6% のときは合格のまま警告行を出力する。
- AC-12 全A / 全B / 全C / 全D の 4 パターンの 1 位が互いに異なる 4 人になり、いずれも「織田信長」ではない(A→D 循環・D→A 循環の結果は参考出力のみで合否に含めない)。
- AC-13 傾向を持つ回答(B-19 のスポットチェック表)で、期待する武将群から 1 位が出る。
- AC-14 「結果を画像で保存」で `sengoku-<武将id>.png`(1080×1920)がダウンロードされる。`file://`、オフライン、画像ファイル無しの状態で必ず成功し、画像に タイトル/武将名/武将画像(代替)/類似度/タイプ/6 軸 が含まれる。生成のたびに Console に 1 行 `ShareCard: usedFallback=false`(フォールバック時は `ShareCard: usedFallback=true reason=<コード>`)が出力され、**Chrome・Edge の `file://` では `usedFallback=false`(= 通常描画が成功している)であること**を手動確認する(B-19 手動確認 9)。結果ダイアログのプレビュー画像は保存操作から 30 秒以上経過しても表示され続ける。
- AC-15 結果確定ごとに当該武将の「本日」「累計」が +1 される。結果画面の再描画、ランキング画面の往復、ウィンドウリサイズ、リロードで再加算されない。
- AC-16 ランキング画面で「本日」「日付別」「累計」の 3 タブを切り替えられ、`1位 〇〇型　N人` 形式で降順表示される。「日付別」では `<select>` に保存済みの日付が新しい順に並び(既定は最新)、過去の日付を選ぶとその日の集計が表示される。件数 0(本日の件数 0、日付が 1 件もない場合を含む)のとき「まだ診断結果がありません」を表示する。
- AC-17 リセットは通常の画面導線には現れず、ランキング画面下部の折りたたみ「運営用メニュー」内にのみあり、確認ダイアログで「リセットする」を押さない限り実行されない(既定フォーカスは「キャンセル」)。
- AC-18 localStorage が使用不可(例外を投げる/無効)でも、診断〜結果表示〜画像保存まで例外なく動作し、ランキング画面に「この環境では集計を保存できません」と表示される。
- AC-19 「最初に戻る」を押すとスタート画面に戻り、`answers` が全て null、結果オブジェクトが破棄され、結果 DOM が空になる。その後の診断に前回の回答・結果が一切影響しない。リロードおよびブラウザの戻る(bfcache 復元含む)でも前の利用者の結果は表示されない。
- AC-20 `IDLE_RESET_MS_*` で設定した無操作時間(既定: 質問 90 秒/結果・ランキング・モーダル表示中 150 秒)の 10 秒前に警告が表示され、満了でスタート画面に戻る。0 を設定すると無効になる。**スタート画面と診断演出中はタイマーを張らない**(スタート画面は戻り先そのものであるため)。
- AC-21 武将画像未設定(`image: null`)または画像の読込失敗(onerror)で自動的に代替カードが表示され、エラーが出ない。
- AC-22 幅 360px・390px・768px・1280px・1920px で水平スクロールが発生しない(`document.documentElement.scrollWidth <= innerWidth`)。かつ**ビューポート 360×540 CSS px**(実機の 640px 級端末でアドレスバー等を除いた可視領域の下限)で、**Q1〜Q15 の全問**について質問画面の `document.documentElement.scrollHeight <= innerHeight`(スクロール不要で質問文・4 択・「前の質問へ」が全て見える)。質問文 30 文字以内・選択肢 26 文字以内は `validateData()` が検査する。測定手順は B-19 手動確認 12。360×540 未満の高さでは縦スクロールを許容する(救済であり合格条件ではない)。
- AC-23 `prefers-reduced-motion: reduce` で装飾アニメーション・カウントアップ・回転が止まり、機能は維持される。
- AC-24 `node tools/check-static.js` が成功する。走査対象は `index.html`・`js/*.js`・**`css/style.css`**。`fetch(`/`XMLHttpRequest`/`WebSocket`/`sendBeacon`/`EventSource`/`importScripts`/`serviceWorker`/`import`・`export` 構文/`type="module"`/`?.`・`??` 演算子/外部 URL(許可は SVG 名前空間 `http://www.w3.org/2000/svg` のみ)/CSS の `@import`・`@font-face` 内の `data:` 以外の `url()`・`url(` に続く `http:`/`https:`/`//`/HTML の相対パス以外の `<link href>`・`<script src>`・`<img src>` が存在しない。詳細パターンは B-19 #14。
- AC-25 スタート/結果/README に免責(エンタメ診断・仮想モデル・類似度の意味)が記載され、README に「localStorage は他の端末と共有されない」「`file://` と `http://` でオリジンが別」が明記されている。
- AC-26 武将詳細モーダルに 名前・生没年・活躍地域・主な功績・有名な出来事・診断用の性格イメージ が表示され、Esc / 閉じるボタン / 背景クリックで閉じ、閉じた後にフォーカスが元のボタンに戻る。
- AC-27 全 20 人の `generals.js` の 6 パラメータは整数 0〜100、任意の 2 人の 6 次元距離は 8 以上、`id` は一意である。
- AC-28 「似ている理由」文は、全武将・任意の回答で、P1(ユーザー側の特徴)と P3(武将側の水準)が**同じ 2 軸**(`sharedAxes`)について述べ、P3 が P1 に出ていない軸に言及しない。さらに、ユーザー水準と武将水準が真逆(high と low)の軸は `sharedAxes` に含めない(B-9、B-19 #11)。
- AC-29 「確認」ダイアログ(リセット)は Esc キー・背景クリックで「キャンセル」と同じ扱いになり、集計は消えない。開いた直後のフォーカスは「キャンセル」にある。
- AC-30 位置バイアス耐性(A-5 (iv))。`node tools/simulate.js` の検査 #15 で、各文字 X∈{A,B,C,D}・p∈{0.7, 0.85}・固定シード・各 20,000 通りの計 8 集団について、p=0.7 では 1 位の最多が 25% 以下、p=0.85 では 40% 以下、いずれの集団も 18 人以上が 1 位として出現する(現行データの実測は B-19: p=0.7 で最大 13.7%、p=0.85 で最大 29.1%、全集団で 20 人出現)。

# Part B. 技術設計

## B-1. 概要と技術スタック(承認後ロック)

静的ファイルのみで構成する SPA 風の単一 HTML。画面は `index.html` 内の複数 `<section>` を `hidden` 属性で切り替える。ロジックはすべて通常の `<script>` で読み込むクラシックスクリプト(IIFE)とし、グローバル名前空間 `window.SG`(Node では `globalThis.SG`)にモジュールを登録する。ES Modules、バンドラ、npm 依存、TypeScript、フレームワーク、外部フォント/CDN は使わない。

- 言語: HTML5 / CSS3 / JavaScript(ES2019 まで。`const/let`、アロー関数、テンプレート文字列、`Array.prototype.flatMap` 可)。対応ブラウザの最低ラインは A1(iOS Safari 15.4 以降)。ES2019 に揃えるのは**コードスタイルの統一のため**で、`?.` / `??` は A1 の環境では動くが使わない方針とし、`tools/check-static.js` が検出して失敗させる(B-19 #14)。
- 描画: DOM + インライン SVG(家紋・城・旗・レーダーチャート・代替カード)+ Canvas 2D(結果カード PNG 生成のみ)。
- 永続化: `localStorage` のランキング集計のみ。
- テスト/ツール: Node.js(標準モジュールのみ。開発環境確認済み: Node v24)。`tools/` 配下。外部パッケージなし。
- フォント: OS 内蔵のみ。**フォント名はすべて単一引用符で囲む**(SVG の `font-family="…"` 属性に埋め込んでも XML が壊れないようにするため。二重引用符は禁止)。見出し(明朝系・筆文字風): `'游明朝','Yu Mincho','YuMincho','Hiragino Mincho ProN','Hiragino Mincho Pro','BIZ UDMincho','MS PMincho','Noto Serif JP',serif`。本文: `'游ゴシック Medium','Yu Gothic Medium','游ゴシック','Yu Gothic','Hiragino Kaku Gothic ProN','Hiragino Sans','Meiryo','Noto Sans JP',sans-serif`。この 2 本の文字列は **`SG.Util.fonts.serif` / `SG.Util.fonts.sans` が唯一の定義**で、Canvas(`ctx.font`)・SVG(`font-family` 属性)はここから参照する(`SG.Fonts` という名前は存在しない)。CSS 側は `:root` の `--font-serif` / `--font-sans` に同じ値を書く。`validateData()` は定数に `"`・`<`・`&` が含まれないことを検査する(含まれたら throw)。この定数は信頼できる固定値なので `esc()` には通さない。
- CSP メタは採用しない(`file://` では `'self'` の解釈がブラウザごとに異なり、スクリプトが読み込まれなくなる恐れがあるため)。代わりに `tools/check-static.js` で外部通信コードを静的に禁止する。

`SG.Util.esc(str)` の仕様: 引数を `String()` で文字列化し、**`&` → `&amp;`、`<` → `&lt;`、`>` → `&gt;`、`"` → `&quot;`、`'` → `&#39;` の 5 文字を、この順で(`&` を最初に)置換**して返す。`null`/`undefined` は空文字列。HTML(`innerHTML` / 属性)と SVG(XML)の両方で使える唯一の文字列エスケープ関数とする(他のエスケープ実装を作らない)。XML の定義済み実体 `&amp; &lt; &gt; &quot;` と数値文字参照 `&#39;` のみを出力するため、`data:image/svg+xml` として XML パースされても有効。

## B-4. 状態管理モデルと画面ステートマシン

### 状態

`app.js` のモジュールスコープに単一の `state` オブジェクトのみ置く。**回答の真実の源は `answers` だけ**で、スコア・順位・グラフ値は派生値(`diagnose(answers)` の戻り値)として必要時に再計算する。質問画面中にスコアを保持・加算しない。

```js
var state = {
  phase: 'START',          // 'START' | 'QUESTION' | 'ANALYZING' | 'RESULT' | 'RANKING'
  answers: new Array(15).fill(null),   // 各要素 null | 0..3
  current: 0,              // 0..14(QUESTION のみ有意)
  diagnosis: null,         // RESULT 中のみ: diagnose(answers) の結果(派生キャッシュ)
  counted: false,          // この診断でランキング加算済みか
  rankingReturnTo: 'START',// RANKING から戻る先: 'START' | 'RESULT'
  cardResult: null,        // 直近の ShareCard.generate() の結果(派生物。プレビュー表示用。閉じる/reset で null)
  cardBusy: false,         // 画像生成中(二重押し防止)
  locked: false,           // 遷移ロック(連打対策)
  runId: 0                 // 診断ごとにインクリメント(タイマー競合防止)
};
```

`state.diagnosis` は `answers` から決定論的に再生成できる派生物であり、`answers` が変わる(= `setAnswer`)ときは必ず `null` に戻す。`reset()` は `state` を初期値で丸ごと置換する(`Object.assign` で各フィールド代入、`runId` のみ +1 して継続)。

| ANY | `pageshow` で `event.persisted` | | START | `reset()`(bfcache 復元対策) |

### 診断演出(ANALYZING)

3 段階の文言を `<p role="status" aria-live="polite">` に順番に表示する。時間は `CONFIG.ANALYZE_TOTAL_MS`(既定 2500 ms)だけで決まり、`step = ANALYZE_TOTAL_MS / 3` として、ANALYZING に入った瞬間(t=0)に 1 つ目の文言を同期的に表示し、`setTimeout` を 3 本(t=`step` で 2 つ目、t=`2×step` で 3 つ目の文言、t=`ANALYZE_TOTAL_MS` で結果へ)張る。既定では 0 / 約 833 / 約 1667 / 2500 ms。`ANALYZE_TOTAL_MS` をどの値にしても 3 つの文言が必ず順に表示される(文言切替間隔の別定数は持たない)。最後の回答の確定から結果表示までは `ANSWER_ADVANCE_MS`(240 ms)+ `ANALYZE_TOTAL_MS` = 約 2.74 秒で、要件の「2〜3 秒程度」に収まる。`ANALYZE_TOTAL_MS` は起動時に 2000〜3000 に clamp する(範囲外なら最も近い端の 2000 または 3000 に丸め、非数なら既定の 2500 にし、いずれも `console.warn`。要件の 2〜3 秒を超える設定を許さないため)。タイマー ID はすべて配列 `timers` に保持し、`clearTimers()` で全解除できる。タイマー内コールバックは冒頭で `if (myRun !== state.runId || state.phase !== 'ANALYZING') return;` を検査する(リセット後に古いタイマーが発火しても無害)。背景は CSS のみ: 回転する大きな家紋(SVG)、広がる金の波紋リング(`@keyframes ripple`)、墨が滲むような円形グラデーションの拡大、舞い落ちる金粉(`::before/::after` の radial-gradient 点を `transform` で動かす)。`prefers-reduced-motion` ではアニメーションを止め、文言の切替のみ行う(時間は同じ)。

### 確認ダイアログ(`#dlg-confirm`)の挙動

`SG.Results.confirm({ message, okLabel })` → `Promise<boolean>`。`showModal()` の直後に **JS で「キャンセル」ボタンへ `focus()`**(`autofocus` 属性には依存しない。Safari の `<dialog>` 内 `autofocus` が不安定なため)。「キャンセル」ボタン・Esc(`cancel` イベントを受けて `preventDefault()` 後に `close('cancel')`)・背景クリック(`dialog` 要素自身が `event.target` のクリック。`<dialog>` 内側は余白なしの内側ラッパー `div.dlg-body` で覆い、本体クリックと背景クリックを区別)はすべて `false` で解決し、閉じたら起動元ボタンへフォーカスを戻す。「リセットする」ボタンのみ `true`。アイドルタイマーが満了して `reset()` が走った場合は、`reset()` が呼ぶ `SG.Results.closeAllDialogs()` がこのダイアログを閉じて Promise を `false` で解決する(リセット操作は実行されない)。`#dlg-confirm` の DOM・イベント・フォーカス戻しは `results.js` が所有する(B-3「`SG.Results` の確定契約」)。

### 連打・二重遷移対策

- 選択肢クリック: `if (state.locked) return; state.locked = true;` → 選択強調 → `setTimeout(advance, 240)`(`CONFIG.ANSWER_ADVANCE_MS`)→ `advance()` 内で `locked=false` と描画。タイマー ID は `timers` に入れ、`reset()` で解除。
- 「いざ、診断開始！」「前へ」「次へ」も同じロックと `runId` 検査を通す。
- `ANALYZING` への遷移は `state.phase !== 'QUESTION'` なら無視(二重遷移防止)。
- 結果確定(`enterResult`)は `if (state.counted) return;` ガードで 1 回だけ加算。

### リセット(`reset()`)

`clearTimers()` → `state` 初期化(`answers.fill(null)`、`current=0`、`diagnosis=null`、`counted=false`、`cardResult=null`、`cardBusy=false`、`locked=false`、`rankingReturnTo='START'`)→ `SG.Results.closeAllDialogs()`(開いている `#dlg-general` / `#dlg-confirm` / `#dlg-card` をすべて閉じる。`#dlg-card` はこの中で `<img>` の `src` 属性を `removeAttribute('src')` で外し、本文を `replaceChildren()` で空にしてから `onClosed` を呼ぶ。`img.src=''` は一部ブラウザでページ自身を再取得するため使わない)→ `state.cardResult = null; SG.ShareCard.dispose()` を直接実行(未 revoke の `blob:` URL を全て `revokeObjectURL`、保留タイマー解除。`onClosed` 経由と二重に走っても冪等)→ `SG.Results.clear(resultRoot)` と `SG.Results.clear(rankingRoot)`(結果 DOM とランキング DOM を `replaceChildren()` で空にする)→ **質問画面の初期化**(`#screen-question` の 4 つの選択肢ボタンの `aria-pressed` を `false` に戻し、選択強調のクラスを除去し、プログレスバーの幅を 0%・`aria-valuenow` を 1 に戻す。質問文・選択肢の文言は次の `renderQuestion(0)` が上書きする)→ スクロール位置を先頭に → `showScreen('START')` → スタートボタンへフォーカス。回答・結果は localStorage/URL/Cookie/`history` に一切書かないため、これで前の利用者の痕跡は残らない。`history.pushState` は使わない(`file://` で SecurityError になるブラウザがあるため)。ブラウザの戻る操作はページ離脱になるだけで、再訪時は常にスタート画面から始まり、bfcache 復元時は `pageshow`(`persisted`)で `reset()` する。

### 無操作タイマー(展示用)

`app.js` 冒頭の定数で制御する。値が 0 以下または数値でない場合は無効(既定値に戻さず「無効」)。

```js
var CONFIG = {
  IDLE_RESET_MS_QUESTION: 90000,   // 質問中: 90秒。0 で無効
  IDLE_RESET_MS_RESULT: 150000,    // 結果/ランキング/モーダル表示中: 150秒。0 で無効
  IDLE_WARN_MS: 10000,             // 満了の何ms前に警告を出すか
  ANSWER_ADVANCE_MS: 240,          // 回答後に次の問へ進むまで
  ANALYZE_TOTAL_MS: 2500,          // 演出の総時間。2000〜3000 に clamp。文言切替は TOTAL/3 刻み(別定数なし)
  COUNTUP_MS: 1000                 // 類似度カウントアップ
};
```

`pointerdown` / `keydown` / `touchstart` / `wheel` / `scroll`(capture, passive)で `lastActivity` を更新し、アイドルタイマーを張り直す。タイマーは**警告用と満了用の 2 本の `setTimeout`** で、ID を配列 `idleTimers`(`[warnId, expireId]`)に保持する。入力のたびに両方を `clearTimeout` し、現フェーズの設定値から張り直す(警告は `満了時間 − IDLE_WARN_MS` 後、満了は `満了時間` 後。`満了時間 ≤ IDLE_WARN_MS` のときは警告を出さず満了だけ張る)。`setInterval` のポーリングはしない。`idleTimers` は `clearTimers()`(`timers` と同時)でも解除する。**START と ANALYZING では張らない**(フェーズ遷移のたびに `armIdleTimer()` がフェーズを見て、QUESTION は `IDLE_RESET_MS_QUESTION`、RESULT/RANKING(開いているダイアログ含む)は `IDLE_RESET_MS_RESULT`、START/ANALYZING は何も張らず既存タイマーを解除する)。満了の `IDLE_WARN_MS` 前に画面下部の `<div role="status">`「操作がないため、まもなく最初の画面に戻ります　[続ける]」を表示し、任意の入力で消す。満了で `reset()`。

## B-5. 15 問の配点設計

### 方針

- 各選択肢は 6 軸の整数配点 `scores = [統率, 行動, 知略, 社交, 慎重, 革新]`。範囲は **−2〜+3**(減点は 2 以下に抑え、極端な負値で特定軸が崩れないようにする)。
- 各選択肢は主軸 1 つに +3(または +2 の補助軸を伴う)、相反する軸に −1〜−2 を置く。行動⇄慎重、革新⇄慎重(安定志向)、社交⇄行動(競争志向)の対立をデータで表現する。
- サンプル Q1〜Q5 は要件で文言と並び(A=積極/B=協調/C=慎重/D=独創 の傾向)が固定されているため動かさない。**Q6〜Q15 は、各問の選択肢の「並び順だけ」を調整して、文字(A/B/C/D)ごとの気質の偏りを相殺した**(各選択肢の文言と配点の組は一切変えない。並びの決め方は下の「並び順の決定方法と位置バイアス対策」)。目的は、要件 §17「同じ回答を選ぶだけで特定の武将になる」を避けること。第 2 版の並びは全A=[65,51,38,25,46,45]・全D=[26,34,47,42,46,54] と文字ごとの偏りが大きく(統率力で文字間 39 点差)、同じ文字を 70% 選ぶ回答で上杉謙信 34%・黒田官兵衛 35% に集中していた(85% では 54%/55%)。本版の並びは文字間の差が軸ごとに 2.9〜8.9 点で、同じ文字を 85% 選んでも 1 位は最大 29% に収まる(B-19 #15)。
- 場面を分散: グループ活動 / トラブル / 価値観 / 勝負 / 企画 / 学校行事 / 友人関係 / 意思決定 / 目標達成 / 初対面 / 緊急事態 / 休日 / ルール / 失敗 / 将来像。歴史知識は不要。
- 選択肢順は**固定**(ランダム化しない)。

## B-6. 正規化方式(具体式)

軸 `k` について、回答 `answers[q]`(0〜3)の配点 `v(q, answers[q], k)` の合計を `raw_k` とする。

```
min_k = Σ_q min_o v(q, o, k)       // 各質問で最小の選択肢を選んだ場合の合計
max_k = Σ_q max_o v(q, o, k)       // 各質問で最大の選択肢を選んだ場合の合計
norm_k = clamp( (raw_k − min_k) / (max_k − min_k) × 100, 0, 100 )
```

- `norm_k` は**丸めずに**保持する(浮動小数。順位計算に使う)。画面表示・カード・グラフのラベルのみ `Math.round`。バーの長さ/レーダー座標は丸め前の値を使う。
- `max_k − min_k > 0` を `validateData()` が全軸で検査する(0 のとき `RangeError('AXIS_RANGE_ZERO')`)。
- 平均的な回答では各軸 37〜46 付近に集まり、一貫した傾向の回答では 2〜100 の端に近づく(例: 行動を最優先で選ぶと行動 100)。A-4 のとおり。

## B-8. 診断アルゴリズムと決定論的ソート(`diagnosis.js`)

```js
var KEYS = ['leadership','action','strategy','social','caution','innovation'];
var MAX_DISTANCE = Math.sqrt(KEYS.length * 100 * 100);

function computeRaw(answers) {            // answers 検証後に合算。入力は変更しない
  assertAnswers(answers);                  // 長さ15・各要素が整数0..3 でなければ RangeError('INVALID_ANSWERS')
  var raw = [0,0,0,0,0,0];
  for (var q = 0; q < 15; q++) {
    var s = SG.Questions.items[q].options[answers[q]].scores;
    for (var k = 0; k < 6; k++) raw[k] += s[k];
  }
  return raw;
}
function normalize(raw) { /* B-6 の式。戻り値: {leadership: float, ...} */ }
function scoreUser(answers) { return normalize(computeRaw(answers)); }

function similarity(user, general) {      // 指定の計算式そのまま
  var d2 = 0;
  for (var i = 0; i < 6; i++) { var e = user[KEYS[i]] - general[KEYS[i]]; d2 += e * e; }
  var d = Math.sqrt(d2);
  var pct = Math.round(Math.max(0, Math.min(100, (1 - d / MAX_DISTANCE) * 100)));
  return { distance: d, distanceSq: d2, similarity: pct };
}

function rankGenerals(user, generals) {   // generals は省略可(テストで人工データを渡す)。省略時は本番データ
  var list = generals || SG.Generals;
  var rows = list.map(function (g, index) {
    var s = similarity(user, g);
    return { general: g, index: index, distance: s.distance, similarity: s.similarity,
             key: Math.round(s.distanceSq * 1e6) };   // 並び替えキー(整数化して浮動小数の誤差を吸収)
  });
  rows.sort(function (a, b) { return (a.key - b.key) || (a.index - b.index); });
  rows.forEach(function (r, i) {
    r.rank = i + 1;
    // 表示用の類似度は直前の順位の値を超えない。並び替えキー(1e-6 単位)が同値の組は二乗距離が 1e-6 未満しか違わず、
    // 距離順と丸め前の類似度順が丸め境界をまたいで逆転する可能性が理論上ゼロではないため、降順の保証をここで 1 行で担保する。
    if (i > 0 && r.similarity > rows[i - 1].similarity) r.similarity = rows[i - 1].similarity;
  });
  return rows;
}

function diagnose(answers) {
  var user = scoreUser(answers);
  var ranking = rankGenerals(user);        // 第 2 引数なし = SG.Generals
  return { user: user, userRounded: roundAll(user), ranking: ranking, top: ranking[0], top3: ranking.slice(0, 3) };
}
```

決定論性の根拠: (1) 入力は `answers` のみで、乱数・`Date`・`Math.random`・グローバル可変状態を使わない。(2) 並び替えは丸め前の二乗距離を 1e-6 単位で整数化したキー昇順、同値は武将配列 index 昇順(**完全な全順序**。`Array.prototype.sort` の安定性にも依存しない)。(3) 表示の類似度は距離の単調減少関数なので、**表示順と類似度の降順は矛盾しない**(同じ整数%が並ぶことはあるが、並びは常にこの順)。(4) 浮動小数の加算順序は軸順固定。(5) `ranking[i].similarity` は `rankGenerals` が最後に直前の順位の値でクランプするため、**常に非増加**(クランプが実際に値を変えるのは、キーが同値の隣接 2 人が丸め境界をまたぐ極端な偶然のときだけで、その場合も差は 1 ポイント未満)。`similarity(user, general)` 単体は指定の式そのままで、クランプしない。

`AXES`(ラベル・説明)と `AXIS_STATS`(理由文用の定数: 乱数回答での平均/標準偏差の整数丸め)も `diagnosis.js` に置く。

## B-9. 「似ている理由」文の自動生成(`reason.js`)

入力: ユーザー丸め前 6 値と 1 位武将。純粋関数・決定論的。

1. 各軸 `k` で `z_u = (user_k − mean_k)/sd_k`、`z_g = (general_k − mean_k)/sd_k`、`diff_k = |user_k − general_k|` を求める。
2. 水準 `level(z)`: `z ≥ 0.6` → high、`z ≤ −0.6` → low、それ以外 → mid。
3. 共通軸の選択: まず各軸の水準(手順 2 を `z_u` と `z_g` それぞれに適用)を求め、**ユーザー水準と武将水準が真逆(一方が high で他方が low)の軸を「不適格」とし、`sharedAxes` から除外する**(P1 が high の句を述べ P3 が「控えめ」と述べる矛盾を構造的に作らない)。不適格でない軸のうち `diff_k ≤ 15` のものを候補とし、`z_u` と `z_g` の符号が同じ(同じ側に平均から離れている)ものを優先して、強さ `(|z_u|+|z_g|)/2` の降順(同値は diff 昇順→軸順)で最大 2 軸を取る。2 軸に満たなければ、不適格でない残りの軸から `diff` 昇順(同値は軸順)で補う(補完された軸の P1 の句は mid の句を使い、`levels.user` の当該要素も `'mid'` として返す。これで「P1 の句 = `levels.user` の水準の句」が常に成り立つ。補完は一様乱数+傾向付き乱数の 1 位の組 60,000 件のうち約 7% で発生する)。それでも 2 軸に満たない(不適格でない軸が 2 本未満。理論上の最終手段で、B-19 #11 で 1 位の組については一度も起きないことを検査する)場合のみ、不適格な軸を `diff` 昇順で補い、戻り値の `usedOppositeFill` を `true` にする(通常は `false`)。
4. 句は**ユーザーの水準**で選ぶ(下表)。
5. 相違軸: `sharedAxes` に含まれない軸のうち `diff_k` が最大のもの(同値は軸順)で、`diff ≥ 25` のとき 1 文足す(共通軸として挙げた軸を「違う」と書かないため `sharedAxes` を除外する)。該当なしなら `diffAxis = null`。

| 軸 | high | mid | low |
|---|---|---|---|
| 統率力 | 周囲をまとめて導く統率力 | ほどよく場をまとめるバランス感覚 | 一歩引いて全体を見守る姿勢 |
| 行動力 | 迷わず決断して動く行動力 | 状況を見ながら動き出す柔軟さ | じっくり構える落ち着き |
| 知略 | 先を読んで考え抜く知略 | 状況に応じて頭を使う判断力 | 直感を大切にするひらめき |
| 社交性 | 人と協力して関係を築く社交性 | ほどよい距離感の人付き合い | 自分の信念を貫くマイペースさ |
| 慎重さ | リスクを見極める慎重さ | 慎重さと大胆さのバランス | 恐れずに踏み出す大胆さ |
| 革新性 | 常識にとらわれない革新性 | 新旧を取り入れる柔軟な発想 | 実績ある方法を大切にする堅実さ |

武将側の水準語(P3 用)は、**武将側の z 値**(手順 1 の `z_g`)に手順 2 の `level()` を適用し、次の表で語に変換する。

| level | 武将側の水準語 |
|---|---|
| high | 高め |
| mid | ほどよい |
| low | 控えめ |

**設計判断(レビュー指摘 5 への対応)**: 武将固定の「結び文(bridge)」は廃止した。固定文は「どの軸が共通か」を知らないため、ユーザーの共通軸が別の軸になったときに P1 と矛盾する(要件 §11・§17 違反)。P1 と P3 が**同じ `sharedAxes[0..1]` から生成される**ことで、構造的に矛盾しないようにする。武将固有の文は史実 1 文(`reason.history`)のみ。

出力段落(`paragraphs`)は次の 3〜4 段:

- P1(診断・ユーザー側): `「あなたは{句A}と{句B}が特徴です。診断のモデルでは、この2点が{武将名}ととても近い結果になりました。」`(句 A・B = `sharedAxes[0]`・`[1]` の**ユーザー水準**の句。手順 3 で補完された軸が含まれるときだけ「ととても近い」を「と近い」にする)。
- P2(史実・武将固有): `「{general.reason.history}」`(武将固有の史実 1 文。例: 「織田信長は、従来のやり方にこだわらず新しい戦い方を取り入れた人物として知られています。」)。必ず「知られています」「とされます」「と伝えられます」で終え、断定を避ける。P2 は診断の軸に言及しない(軸ラベルの語を含めない。ただし史実の説明として自然な語は可)ため、P1・P3 と矛盾しない。
- P3(診断・武将側テンプレート): `「{武将名}も診断上は{軸ラベルA}が{水準語A}で、{軸ラベルB}も{水準語B}タイプです。この2つの軸の数値が近いことが、今回の診断での共通点です。」`(軸ラベル A・B = `sharedAxes[0]`・`[1]` の `AXES[].label`、水準語 = 上表。**P3 に出てよい軸ラベルは `sharedAxes` の 2 つだけ**)。結びの文は「水準語が同じ」ではなく「数値が近い」ことを述べるので、ユーザー水準と武将水準が high と mid のように隣り合う場合(約 26% の結果で起きる)でも P1・P3 の文面と矛盾しない。例: `「織田信長も診断上は革新性が高めで、行動力もほどよいタイプです。この2つの軸の数値が近いことが、今回の診断での共通点です。」`
- P4(相違、条件付き): `「一方、{軸ラベル}は{武将名}のモデルのほうが{高め/低め}です。」`(`diffAxis` の軸。ユーザーより武将が大きければ「高め」、小さければ「低め」)。

`build()` の戻り値は `paragraphs`(P1〜P4、P4 は条件付き)、`sharedAxes`(軸キー 2 つ)、`levels`(`user`/`general` それぞれ 2 要素の水準 `'high'|'mid'|'low'`)、`diffAxis`(キーまたは null)、`usedOppositeFill`(boolean。テスト用)。`sharedAxes` は手順 3 により**常に長さ 2**(候補が足りなければ diff 昇順で補う)。

画面では段落の後に小さく「※ 武将の紹介は一般的な史実の説明、診断の数値と解釈はアプリ独自の仮想モデルです。」を固定表示し、史実と診断解釈を混同させない。`reason.history` は 20 人それぞれ固有の文を書く(定型コピーの流用禁止。`validateData()` が重複文を検出して失敗させる)。

## B-12. ランキング(localStorage)

### スキーマ(`storage.js`)

キー: `sengoku-personality:v1:stats`(名前空間付き。`file://` の Chrome は全 `file://` で localStorage を共有し得るため衝突回避)。

```json
{ "v": 1,
  "total": { "oda-nobunaga": 25, "tokugawa-ieyasu": 18 },
  "daily": { "2025-11-01": { "oda-nobunaga": 10, "tokugawa-ieyasu": 7 } } }
```

件数は 1 以上の整数のみ保存(0 は書かない)。キーは `SG.Generals` の id に限る。日付キーは `YYYY-MM-DD`(`getFullYear/getMonth/getDate` をゼロ埋め。UTC 変換はしない)。**回答・結果・個人情報は保存しない**(`increment` の引数は武将 id のみで、構造的に回答を渡せない)。

### API と動作

`create(storageLike, clockFn)` がストアを返す(テストでモックを注入)。引数の扱い:

- `storageLike` が `getItem/setItem/removeItem` を持つオブジェクト → それを使う(プローブ: `setItem/removeItem` の往復を `try/catch`。例外ならメモリ縮退)。
- `storageLike === null` → 最初から**メモリ内のみ**。
- `storageLike === undefined`(省略)→ `typeof window === 'undefined'` なら **`localStorage` に一切触れずメモリ内のみ**(Node の `require` で警告や例外が出ない)。ブラウザなら `window.localStorage` を `try/catch` でプローブして使う(`window.localStorage` の参照自体が SecurityError を投げる環境も `try` 内)。
- メモリ内のみのとき、同じ API を提供し `isPersistent()===false`。

**モジュールのロード時には `create()` を呼ばない**(副作用なし)。アプリ用の既定ストアは `SG.Storage.getDefault()` が**初回呼び出し時に 1 度だけ**生成してキャッシュする(`app.js` の `init()` が呼ぶ)。`tools/simulate.js` は `getDefault()` を呼ばず、`create(mock, clock)` / `create(null, clock)` のみを使う。

- `increment(id)`: id 検証 → 最新を読み込み(read-modify-write。複数タブの上書きを最小化)→ `total[id]++`、`daily[today][id]++` → `setItem`。失敗(容量/無効化/例外)は捕捉し、メモリ値だけ更新して `isPersistent=false` にし `console.warn`。戻り値は `{ ok: boolean }`。例外を外へ出さない。
- `getCounts(scope)`: `scope` は `'total'`、`'today'`、または日付文字列 `'YYYY-MM-DD'`(正規表現 `^\d{4}-\d{2}-\d{2}$`)。`'today'` は `todayKey()`(= `clockFn()` のローカル日付)に解決して日付指定と同じ処理に入る。`[{ id, count }]` を件数降順、同数は `SG.Generals` の配列順で返す(0 件の武将は含めない)。**上記以外の `scope`(`null`・数値・未知の文字列・形式違反)と、`daily` に存在しない日付は、例外を投げず空配列を返す。** `getTotalPlayers(scope)` は同じ `scope` 規則で件数の合計(不正な `scope`・存在しない日付は 0)。
- `listDates()`: `daily` に保存されている日付キー(件数 1 以上の日のみ。形式 `YYYY-MM-DD` を満たさないキーは読込時検証で捨てているので出ない)を**降順(新しい順。文字列の辞書順降順で正しい)**の配列で返す。0 件なら `[]`。読込のたびに最新の保存内容から作る(キャッシュしない)。
- `reset()`: キー削除+メモリ初期化。例外は捕捉。
- 読込時検証: JSON.parse 失敗/`v!==1`/型不一致 → 空として扱い、破損した生文字列は `...:stats:corrupt` に退避(失敗は無視)。未知の id・非整数・負数・0 は読み飛ばして修復。`daily` のキーが `^\d{4}-\d{2}-\d{2}$` に一致しない場合もその日付ごと読み飛ばす(日付別タブに不正な日付が出ないようにするため)。

### 二重カウント防止

加算は `app.js` の `enterResult()` の 1 か所のみ。`state.counted` が false のときだけ `store.increment(top.general.id)` を呼び、直後に `counted=true`(書込に失敗しても true)。再描画・ランキング往復・リサイズ・`pageshow`(リセットされる)・リロード(状態が消えスタートに戻る)のいずれでも再加算されない。`reset()` で `counted=false` に戻るのは新しい診断に備えるため。

### ランキング画面(`results.js: renderRankingScreen`)

見出し「本日の戦国武将ランキング」(日付別は「戦国武将ランキング(YYYY年M月D日)」、累計は「戦国武将ランキング(累計)」)、タブ `role="tablist"` は**「本日」「日付別」「累計」の 3 つ**(「本日」のタブ内に「YYYY年M月D日」を小さく併記)。画面ローカルの表示状態は `{ scope: 'today' | 'date' | 'total', date: string | null }` で、`renderRankingScreen` の閉包に持つ(永続化しない)。初期は `scope='today'`。**「日付別」を選ぶと、タブの下に `<select aria-label="日付を選ぶ">` を表示する**: 選択肢は `store.listDates()`(新しい順)の各日付を「YYYY年M月D日(N人)」(N = `getTotalPlayers(その日付)`)の表記で並べ、既定は先頭(最新の日付)。選択を変えると `date` を更新して一覧だけを再描画する(加算はしない)。`listDates()` が空のときは `<select>` を出さず「まだ診断結果がありません」を表示する。日付別の一覧は `store.getCounts(date)`、本日は `store.getCounts('today')`、累計は `store.getCounts('total')`。診断人数、`1位 織田信長型　25人` 形式の `<ol>`(上位 10 件+「すべて表示」)、横バー付き。0 件は「まだ診断結果がありません」。`isPersistent()===false` なら注意文「この環境では集計を保存できません(このページを閉じると消えます)」。注記「集計はこの端末・このブラウザの中だけに保存され、他の端末とは共有されません」。下部に `<details>`「運営用メニュー」(小文字・低コントラスト寄りの控えめな見た目)があり、中に「集計をリセット」ボタン。押すと `#dlg-confirm`(「集計をすべて消します。この操作は取り消せません。」+「キャンセル」/「リセットする」(深紅))。**フォーカスは JS で「キャンセル」に当て、Esc・背景クリックは「キャンセル」と同じ扱い**(挙動の詳細は B-4「確認ダイアログの挙動」)。「リセットする」のみ `store.reset()` 後に再描画。「戻る」ボタンで `rankingReturnTo` に戻る。

## B-13. 結果画像の保存(`share-card.js`)と taint 回避

方針: 画像は**描画元をすべてローカルで生成**し、キャンバスが汚染(tainted)される経路を作らない。

- 武将画像は `SG.Crest.svg(general)` が返す自己完結 SVG(外部参照・`<foreignObject>`・`<image>`・`<style>` なし、`width`/`height`/`xmlns` 明記、**XML として整形式**。B-14)を `data:image/svg+xml;charset=utf-8,` + `encodeURIComponent(svg)` の data URI にして `new Image()` に読み込み、`drawImage` する。data URI の SVG は、主要ブラウザ(Chrome/Edge/Firefox)では `file://` でもキャンバスを汚染しないとされるが、**これは設計上の前提でありブラウザごとに差があり得るため、下記の汚染検知+フォールバック+手動確認(B-19 手動確認 9)で担保する**。Safari 等で汚染される場合も、フォールバックにより保存自体は成功する。
- `general.image` に実画像が設定されている場合: `data:` URI のときのみカードにも使う。通常のファイルパスは `file://` では汚染源になるため、**カードでは使わず代替カードを使う**(`location.protocol` が `http:`/`https:` のときだけ同一オリジンの画像を試す)。READMEに「`file://` ではカード画像は代替カード、画面表示は実画像」「カードにも実画像を入れたい場合は `data:` URI 化する」と明記。
### `generate()` の制御フロー(「必ず成功」の構造)

`generate(diagnosis)` は 2 つの描画モードを持つ。**`full`**: 家紋 SVG(data URI)を `drawImage` する通常版。**`primitive`**: 画像(`Image`/`drawImage`)を一切使わず、Canvas の図形・文字 API だけで武将パネル(`createLinearGradient` の背景+金の二重枠+`crest.display` 文字の大書+円形の簡易家紋)を描く版。`primitive` は `SG.Util` など他モジュールの定数にも依存せず、フォントは直書きの `'serif'` / `'sans-serif'` を使う(定数参照の失敗で落ちない)。

1. `renderCard('full')` を実行する。この中の**描画処理全体(Canvas 作成〜`drawImage`〜テキスト描画〜検知〜書き出し)を 1 つの `try/catch` で包む**。次のいずれかが起きたら失敗コードを決めて 2 へ進む:
   - `svg-load-error`: SVG の `Image.onerror`。
   - `svg-timeout`: SVG の読込が 10 秒(`share-card.js` 先頭の定数 `SVG_LOAD_TIMEOUT_MS = 10000`)以内に終わらない。
   - `tainted`: 描画後の `ctx.getImageData(0,0,1,1)` が例外(SecurityError)。
   - `draw-exception`: 描画中の任意の例外(`SG.Util.fonts` 参照の `TypeError`、`ctx` 取得失敗 等を含む)。
   - `export-error`: `toDataURL('image/png')` または `toBlob` の例外/`null` 結果で `dataUrl` が得られない。
2. `renderCard('primitive')` を実行する(同じく全体を `try/catch`)。成功すれば `usedFallback:true, reason:<1 のコード>` で resolve。
3. 2 も失敗した場合のみ reject(Canvas 自体が使えない環境だけ。B-15)。
4. 成功時の書き出し: `dataUrl = canvas.toDataURL('image/png')` を必ず取得(これが成功しなければその描画は失敗扱い)。`blob` は `canvas.toBlob(cb, 'image/png')` で取得し、非対応/`null` の場合は `blob: null` のまま返してよい(ダウンロードは `dataUrl` にフォールバック)。戻り値は常に `{ blob, dataUrl, usedFallback, reason }`。
5. **可視化(レビュー指摘 8)**: 成功した生成の末尾で 1 行だけ Console に出力する。通常版は `console.info('ShareCard: usedFallback=false')`、フォールバック版は `console.warn('ShareCard: usedFallback=true reason=' + reason)`。reject 時は `console.error('ShareCard: failed ' + message)`。これにより「常時フォールバックしているのに PNG は出るので気づかない」状態を手動確認で検出できる(B-19 手動確認 9)。

`general.image`(実画像)がカードに使われない場合(`file://` の通常パス)は、失敗ではなく仕様なので `usedFallback` は false のまま(代替カードは `full` モードの通常描画)。

### 保存とプレビュー(URL の寿命を分離する)

- **プレビュー `<img>` と「保存」リンク(`<a download>`)の `src`/`href` は `result.dataUrl`**(`toDataURL('image/png')`)を使う。data URL は文字列そのものでありリボークが不要なため、30 秒後にも壊れず、iOS Safari の長押し保存や再保存が機能する。
- **blob URL はプログラムによる自動ダウンロード専用**: `download(result, filename)` が `result.blob` から `URL.createObjectURL(blob)` → 一時 `<a download="sengoku-{id}.png">` を生成 → `click()` → `setTimeout(revoke, 30000)`。`blob` が null の場合は `dataUrl` を `href` に使う。未 revoke の URL とタイマーは `ShareCard` 内部の配列で管理し、`dispose()` が全て revoke・解除する。
- 生成が成功したら、自動ダウンロードを試みると同時に `#dlg-card` を開き、プレビュー画像・「保存」リンク・案内文「保存されない場合は、画像を長押し(または右クリック)して保存してください」を表示する。
- **担当の分割(B-3「`SG.Results` の確定契約」)**: `#dlg-card` の描画と閉じる処理は `results.js`(`openCardPreview(result, { onClosed })` / `closeCardPreview()`)、`state.cardResult` と blob URL の寿命は `app.js`(+ `SG.ShareCard.dispose()`)が持つ。`app.js` の `onSaveCard` ハンドラは `generate()` → 成功したら `state.cardResult = result` → `SG.ShareCard.download(result, 'sengoku-{id}.png')` → `SG.Results.openCardPreview(result, { onClosed: onCardClosed })` の順に呼ぶ。`onCardClosed` は `state.cardResult = null; SG.ShareCard.dispose();` を行う関数。`#dlg-card` を閉じる(閉じるボタン・Esc・背景クリック・`closeCardPreview()`・`closeAllDialogs()`)と、`results.js` が `<img>` の `src` 属性を `removeAttribute('src')` で外し、本文を `replaceChildren()` で空にして、`onClosed` を 1 回だけ呼ぶ。`reset()` は `closeAllDialogs()` の後に同じ 2 行を直接実行する(冪等)。次の生成時に前の `cardResult` が残っていれば、`openCardPreview` が先に同じ破棄を行うので、メモリに保持される結果は常に 1 件だけ。
- 生成中は `state.cardBusy = true` にして `SG.Results.setSaveBusy(resultRoot, true)`(ボタンを無効化し「作成中…」と表示)、完了/失敗の `finally` で `cardBusy = false` と `setSaveBusy(resultRoot, false)`。完了/失敗で復帰(二重押し防止。`cardBusy` が true の間の再クリックは無視)。生成は `await` で非同期だが、`runId` を取っておき、完了時に `runId` が変わっていれば(`reset()` 済み)結果を破棄してダイアログも開かない。

## B-14. 代替カード(SVG)設計(`crest.js`)

`SG.Crest.svg(general, { idPrefix, title })` は viewBox `0 0 300 400` の自己完結 SVG 文字列を返す(`xmlns` 付き、`<defs>` の ID は `SG.Util.uid()` による接頭辞で画面内の複数インスタンス間の重複を避ける)。`title` オプションが空でない文字列で渡されたときだけ、`<svg>` の最初の子要素として `<title>` + `SG.Util.esc(title)` + `</title>` を出力する(`<svg>` 自体には `role`/`aria-*` 属性を付けない。画面に埋め込む側のラッパー `div` が `role="img"` と同じ文言の `aria-label` を持つ)。`title` が省略・空のときは `<title>` を出力しない(結果カード用の `dataUri()` はこちら)。`<title>` は通常の XML 要素なので、`assertWellFormedSvg()` の検査対象に含まれる。

**XML 整合性の規則(レビュー指摘 7)**: この文字列は HTML にインライン埋め込みされるだけでなく、`data:image/svg+xml` として `Image` に読まれる場合は **XML としてパース**される(HTML より厳格で、不正だと `onerror` になり保存が静かにフォールバックへ落ちる)。したがって生成コードは次を守る。
- 全ての属性値は**二重引用符**で囲む。値に二重引用符を含めない(フォント定数は B-1 のとおり単一引用符のみ)。
- 動的文字列(`general.name`、`crest.display`、`crest.glyph`、色コード等、データ由来の全て)は必ず `SG.Util.esc()`(5 文字エスケープ。B-3)を通す。`SG.Util.fonts.*` は固定の信頼値なのでそのまま埋め込む(`validateData()` が `"`・`<`・`&` を含まないことを保証)。
- 使ってよい実体は `&amp; &lt; &gt; &quot; &#39;` のみ。`&nbsp;` 等の HTML 実体は使わない。
- 全ての要素を閉じる(空要素は `<circle … />` の自己閉じ形式)。`<br>`・`<style>`・CDATA・コメントは使わない(書式は属性で指定。`paint-order="stroke"` 等はプレゼンテーション属性として書く)。
- `<image>`・`<foreignObject>`・`<script>`・外部 `href` は使わない。

2. 和柄(`pattern`): `seigaiha`(青海波=同心円弧の千鳥)、`asanoha`(麻の葉=六角と放射線)、`shippo`(七宝=重なる円)、`uroko`(鱗=三角の千鳥)、`kikkou`(亀甲=六角形の敷き詰め)、`ichimatsu`(市松)。`<pattern>` 要素で accent を不透明度 0.10 で敷く。

5. 下部の帯: `general.name` を横書き(font-size 18、中央、y≈385)で小さく表示し、帯の上下に accent の細罫線。外周に二重フレーム(accent)と四隅の飾り。

## B-17. 不変条件と所有レイヤー

| 不変条件 | 所有レイヤー | 理由 |
|---|---|---|
| 状態は `answers[15]` のみ。スコアは毎回全再計算 | `app.js`(状態の唯一の所有者)+ `diagnosis.js`(純粋関数) | 二重加算を構造的に不可能にする(加算するコードが存在しない) |
| 同じ回答 → 同じ結果、表示順 = ランキング順 | `diagnosis.js` | 純粋関数+全順序ソート。UI は並び替えず `ranking` をそのまま使う |
| 結果確定あたりランキング加算は 1 回 | `app.js` の `state.counted` | 加算タイミングを知っているのは状態遷移だけ。`storage.js` は冪等性を知らない |
| 回答・結果は永続化されない | `storage.js` の API 形状(武将 id のみ受け付ける) | 他の層が誤って保存できない |
| 診断・保存が localStorage の可否に依存しない | `storage.js`(内部で縮退) | 呼び出し側の分岐を不要にする |
| 外部通信ゼロ | `tools/check-static.js`(CI 代わり)+ 設計ルール | 実行時には検出できないため静的に守る |
| 画像カードが必ず保存できる | `share-card.js`(汚染検知+フォールバック) | ブラウザごとの taint 差異をこの層で吸収 |
| 前の利用者のデータが残らない | `app.js: reset()` + `results.js: clear()` | DOM とメモリ双方を一箇所で破棄 |

## B-21. リスクと既知の制限

- ユーザー値の分布が中央寄りになる(A-4)。武将値を同じ尺度に置いて対処済み。レーダー上の武将は最大でも 72 程度になる旨を凡例に「診断用の仮想モデル値」として注記する。
- 類似度の表示は 1 位でも 76〜99%、傾向の強い回答で 70%台後半になり得る(上位に並ぶ武将の差は数ポイント)。これは「近さ」を表すモデル値であり、確率ではない旨を注記する。
- `file://` 上の実画像はカード PNG には載らない(代替カードで保存される)。`data:` URI 化で回避可能。実画像を採用する場合の今後の課題として README に残す(B-20)。
- 位置バイアス(第 3 版): 並び順の調整で文字別の偏りを相殺したが、これは「統計的に偏りが小さい」ことの確認であり、特定の人が好みのパターンを選べば必ず特定の武将に行く、という可能性が完全にゼロになるわけではない(例: 「全A」は直江兼続、「全D」は長宗我部元親という固定の結果になる。これは同じ回答なら同じ結果、という要件 §17 の決定論そのものである)。要件の禁止事項は「**同じ回答を選ぶだけで特定の武将になる**」ことのうち、(a) 1 つの文字を選び続ける回答集団が 1 人に集中すること(#15 で 29% 以下を確認)、(b) 4 つの単調パターンが同じ武将になること(#4 で相異を確認)を指すと解釈して検査している。
- ダウンロード履歴・保存済み PNG・LAN 公開の運用上の注意は B-20 に記載(日替わりの削除、信頼できる Wi-Fi への限定、スマホの結果は展示 PC のランキングに入らない)。
- ブラウザの Back による離脱は防げない(`pushState` を使わない設計判断)。復帰時は必ずスタートから。
- 武将の史実記述は実装者が執筆するため、事実確認(B-7 のルール)が必要。
- **未検証の前提(実装後に実機で確認する。設計はいずれも失敗しても機能が継続する作りにしてある)**: (1) data URI の SVG が各ブラウザの `file://` でキャンバスを汚染しないこと(B-13。汚染されても `primitive` 版で保存は成功し、`usedFallback` で可視化される)。(2) `file://` からの blob URL ダウンロードと iOS Safari の `download` 属性の挙動(プレビューの `dataUrl` 長押しで代替)。(3) bfcache 復元時の `pageshow` の挙動(`persisted` でない復元でも状態は常にスタートから始まる)。(4) Firefox/Safari の `file://` での localStorage 保持(不可でもメモリ縮退で動作し、画面に注意文を出す)。(5) `history.pushState` が `file://` で失敗するブラウザがあるという判断(使わないので無害)。
- 画面描画(`chart.js`・`results.js`・`app.js`・`share-card.js`)は DOM/Canvas 依存のため自動テストの対象外。二重カウント・リセット・無操作タイマー・確認ダイアログは手動確認(B-19)で担保する。純粋関数(`diagnosis.js`・`reason.js`・`storage.js`・`crest.js`・`util.js`)は Node で自動テストする。
