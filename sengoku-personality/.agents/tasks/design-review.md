## 指摘事項

### 1. [MEDIUM] 類似度の整数表示が上位で飽和し、TOP3 の順位が見た目で区別できない。B-21 の記述も事実と異なる

**場所**: B-8(`similarity`・`rankGenerals`)、B-11(結果画面 6.)、B-12、B-21 の 2 番目の項目、AC-8、AC-10

**問題**: 要件 §8 の式(`1 - d/√60000`)をそのまま使うと、20 人の武将が互いに 8.7 以上離れているだけで、ユーザーの値も 20 人の領域の内側に集まるため、距離の差が小さくなる。設計書の配点・パラメータで、一様乱数の回答 50,000 通り(seed 777)を診断して測った。

- 1 位と 2 位の表示%が同じになる割合: **39.3%**
- 1 位と 3 位まで同じ表示%になる割合: **13.5%**
- 1 位と 2 位の差の中央値: **1 ポイント**(90 パーセンタイルでも 2)
- 1 位と 3 位の差の中央値: **1 ポイント**(90 パーセンタイルで 3)

つまり結果画面は「1 位 90%、2 位 90%、3 位 89%」のような表示が日常的になる。要件 §12 の表示例(92% / 86% / 81%)の差は 5 ポイントずつで、体感がかなり違う。同点時の並び順は決定的に決まるが(B-8)、来場者には「なぜこの順なのか」が見えない。B-21 は「上位に並ぶ武将の差は数ポイント」と書いているが、実測では 1〜2 ポイントで、リスクを小さく見せている。TOP3 や 20 人一覧で同じ%が並んだときの表示規則もない。

**修正案**: 式(要件 §8)は変えずに、表示だけで差を見えるようにする。

1. `rankGenerals` の各行に、丸め前の割合を 1 桁に丸めた `similarityExact` を追加する。

```js
var pctRaw = Math.max(0, Math.min(100, (1 - d / MAX_DISTANCE) * 100));
// similarity (整数) は従来どおり。AC-10 と結果カード PNG の大見出しはこちらを使う
// similarityExact は距離の単調減少関数なので、順位と矛盾しない
row.similarityExact = Math.round(pctRaw * 10) / 10;
```

2. 結果画面の大見出し「類似度 92%」は整数のまま(要件 §10 の例どおり)。TOP3 と 20 人一覧は `similarityExact` を小数 1 桁で表示する(例: `90.4%` / `89.7%` / `89.2%`)。
3. AC-8 に「TOP3 と 20 人一覧の `similarityExact` が非増加であること」を追加する。`simulate.js` #6 の検査対象に加える。
4. `simulate.js` に検査 #16「上位の差」を追加し、1 位と 2 位の整数%が同じになる割合、`similarityExact` が同じになる割合、差の 50/90 パーセンタイルを出力する(合否ではなく表示のみ。`similarityExact` が同じになる割合が 5% を超えたら WARN)。
5. B-21 の該当項目を「上位 3 人の差は中央値 1 ポイント程度。整数%では 39% の結果で 1 位と 2 位が同じ表示になるため、TOP3 と一覧は小数 1 桁で表示する」に書き換える。

### 2. [MEDIUM] 集団全体の回答傾向(協調・慎重寄り、大胆寄り)に対する偏り検査がなく、軽い傾きで特定の武将に集中する

**場所**: A-5、AC-11、AC-30、B-19 #2・#3・#15、B-21

**問題**: 分布検査は 3 種類ある。(#2)全ての選択肢が等確率、(#3)試行ごとに軸の重みを引き直す傾向付き乱数、(#15)選択肢の文字(A〜D)への偏り。いずれも、集団全体が同じ方向へ傾く場合を含まない。#3 は試行ごとに重みの符号が変わるので、集団として打ち消し合う。実際の来場者は、「仲間と協力」「計画的」のような協調・慎重寄りの選択肢を選びやすいなどの傾きが十分あり得る(自己評価の望ましさバイアス)。

設計書のデータで、選択肢の選択確率を `exp(β·Σ w_k·配点_k)` に比例させた集団(各 30,000 通り、固定シード)を測った。

| 集団(w は 統率,行動,知略,社交,慎重,革新) | β | 最多 | 20 人中 0.1% 以上で出現 | 最少 |
|---|---|---|---|---|
| 協調寄り(0,0,0,+1,+1,−1) | 0.10 | 徳川家康 22.8% | 20 人 | 織田信長 0.17% |
| 協調寄り | 0.15 | 徳川家康 34.0% | 15 人 | 織田信長 0.01% |
| 協調寄り | 0.20 | 徳川家康 42.7% | 12 人 | 長宗我部元親 0.00% |
| 大胆寄り(+1,+1,0,0,−1,+1) | 0.10 | 長宗我部元親 17.9% | 19 人 | 北条氏康 0.08% |
| 大胆寄り | 0.15 | 長宗我部元親 26.2% | 16 人 | 北条氏康 0.01% |
| 社交・慎重・知略の単軸 | 0.10 | 10〜11% | 20 人 | 1.5% 以上 |

β=0.10 は、1 つの選択肢が他より約 1.5〜1.8 倍選ばれる程度の傾き。それでも協調寄りでは信長がほぼ出なくなる。要件 §17「一部の武将がほとんど出現しない」「特定の武将に集中する」に対して、現行の検査では検出できない。現行データは β=0.10 で閾値内だが、余裕は 2 ポイント程度しかない。

**修正案**: `simulate.js` に検査 #16「集団バイアス耐性」を追加する(AC-32 を新設)。

- 集団: 協調寄り `[0,0,0,1,1,-1]`、大胆寄り `[1,1,0,0,-1,1]`、社交 `[0,0,0,1,0,0]`、慎重 `[0,0,0,0,1,0]`、知略 `[0,0,1,0,0,0]`。
- 生成: `mulberry32(20240701 + 集団index×10 + round(β×100))`、各 20,000 通り。1 問ごとに 4 択の重み `exp(β · Σ_k w_k·scores_k)` を計算し、`r = rnd()·Σ重み` から選択肢を順に引く。乱数の消費は 1 問につき 1 回。
- 合格(β=0.10): 1 位の最多が 25% 以下、かつ 0.1% 以上で出現する武将が 18 人以上(現行データは協調寄り 22.8% / 20 人、大胆寄り 17.9% / 19 人で合格する)。
- 警告のみ(β=0.15): 最多が 35% を超えたら `WARN`(現行は協調寄り 34.0%)。集団ごとの最多と出現人数を表で出力する。
- B-21 に「集団全体が協調・慎重寄りに傾くと家康・氏康に集中する(β=0.15 で家康 34%)」と既知の制限を書き、調整の手順(B-19)に「#16 が落ちたら、その集団で最少の武将を集団の重心に近づける」を追記する。

### 3. [NIT] B-9 手順 3 の候補の選び方に 2 通りの解釈があり、補完率の実測値が再現できない

**場所**: B-9 手順 3、B-19 #11、B-19 再計測結果の「理由文」

**問題**: 手順 3 は「`diff_k ≤ 15` のものを候補とし、符号が同じものを優先して」と書いている。符号が異なるが `diff ≤ 15` の軸が候補なのか、補完用の残りに入るのかが読み取れない。1 位の組 30,000 通りで 2 通りに実装して比べた。

- 字義どおり(符号が異なる軸は候補にしない): 補完 **11.6%**
- 符号が異なる軸も 2 段目の候補にする: 補完 **7.1%**(設計書の「約 7%」と一致)

どちらも `usedOppositeFill` は 0 件で AC-28 を満たすが、同じ入力で違う文章が出る。さらに、補完された軸は `diff` が最大 29 でも、P3 は「この2つの軸の数値が近いことが…共通点です」と言い切る。字義どおりの解釈で `sharedAxes` の 3.9% が `diff > 15` だった。

**修正案**: 手順 3 を次の擬似コードで確定する(上の「2 段目の候補にする」解釈)。

```js
var eligible = axes.filter(function (a) { return !isOpposite(a); });
var near = eligible.filter(function (a) { return a.diff <= 15; });
function byStrength(a, b) { return (strength(b) - strength(a)) || (a.diff - b.diff) || (a.idx - b.idx); }
var tier1 = near.filter(sameSign).sort(byStrength);
var tier2 = near.filter(notSameSign).sort(byStrength);
var picked = tier1.concat(tier2).slice(0, 2);
// 足りなければ eligible の残りを diff 昇順(同値は軸順)で補い、補った軸の levels.user は 'mid'
```

補完された軸 `diff > 15` を含む場合は、P3 の結びを「…数値が近いことが共通点です」から「…は、今回の診断では比較的近い軸でした」に切り替える(`diff > 15` の軸が 1 つでもあるとき)。

### 4. [NIT] TOP3 カードと「くわしく見る」ボタンのクリックが二重に発火する。ダイアログの再オープンも未規定

**場所**: B-11(結果画面 6.)、B-3(`openGeneralDialog`)

**問題**: 「くわしく見る」ボタンを含むカード全体もクリック可、と書かれている。カードとボタンの両方にハンドラを付けると、ボタンのクリックがカードに伝わって `openGeneralDialog` が 2 回呼ばれる。`<dialog>.showModal()` は、実装によっては既に開いているダイアログに対して `InvalidStateError` を投げる。さらに、カード(クリック可能な要素)の中にボタンを置くと、キーボードでは同じ操作に 2 回止まる。

**修正案**: ハンドラは結果画面のルート 1 か所に置く(イベント委譲)。カードは `<li>` とし、内側のボタンのみがフォーカスを受ける。カード全体のクリックは `closest('[data-general-id]')` で受ける。`openGeneralDialog` の冒頭に `if (dlg.open) return;` を置き、`showModal` が例外を投げたら `open` 属性を付ける(B-15 の既存規則)。20 人一覧の行も同じ規則にする。

### 5. [NIT] `toBlob` に時間切れがなく、保存ボタンが「作成中…」のまま戻らない恐れがある。SVG 読込の 10 秒も NFR-3 と食い違う

**場所**: B-13(`generate()` の制御フロー)、NFR-3

**問題**: `svg-timeout`(10 秒)はあるが、`toBlob(cb)` のコールバックが呼ばれない場合の時間切れがない。その間 `state.cardBusy` が立ったままで、ボタンが無効化されたままになる。また NFR-3 は「結果カード生成は 2 秒以内(目安)」だが、SVG の読込に失敗した場合は 10 秒待ってから `primitive` 描画へ進むため、体感は 10 秒を超える。

**修正案**: `toBlob` を `Promise.race([toBlobPromise, timeout(3000)])` で包み、時間切れは `blob:null` で続行する(`dataUrl` が主経路のため問題ない)。`SVG_LOAD_TIMEOUT_MS` を 4000 に下げる(data URI の SVG は読込が即時なので、4 秒かかるなら失敗とみなしてよい)。NFR-3 に「失敗時のフォールバックを含めて 5 秒以内」と追記する。

### 6. [NIT] 1080×1920 の PNG を data URL にしたときの長さの上限が未検証

**場所**: B-13(保存とプレビュー)、B-21(未検証の前提)

**問題**: プレビューの `<img>` と「保存」リンクは `result.dataUrl` を使う。背景に青海波、グラデーション、家紋を重ねた 1080×1920 の PNG は、ブラウザや内容によって数百 KB から 2MB 前後になり得る。Chromium 系は URL 全体の長さに約 2MB の上限があり、`<a download>` や `<img>` に大きな data URL を渡したときの挙動は、ブラウザと版によって異なる可能性がある。この前提は B-21 の「未検証の前提」に入っていない。主経路は `blob` のダウンロードなので、失敗しても保存自体は成功し得るが、プレビューが空になる恐れがある。

**修正案**: 手動確認 9 に「生成した PNG のバイト数と `dataUrl.length` を記録する」を追加し、`dataUrl.length` が 1,500,000 を超えたときは、プレビューの `<img>` に `URL.createObjectURL(blob)` を使い(`blob` が非 null のとき)、`onClosed` で revoke する分岐を B-13 に追記する。B-21 の未検証の前提に (6) として加える。

### 7. [NIT] スマホ縦画面の規則が質問画面以外で薄い(結果・開始・ダイアログ)

**場所**: B-10、B-11、NFR-8

**問題**: 質問画面は高さ予算まで書かれているが、他の画面は「1 カラム、ボタン全幅」止まり。次が未規定で、実装者ごとに崩れ方が変わる。

- 武将名(`<h2>`、特大)のフォントサイズ。6 文字の「長宗我部元親」が 320px 幅で折り返すか、はみ出すか。
- レーダーの `<svg>` の幅(`width:100%; max-width:360px; height:auto` か)。
- 武将詳細ダイアログと `#dlg-card` の最大高さ、内部スクロール、閉じるボタンの位置(スクロールで見えなくなるか)。

**修正案**: B-10 に次を追記する。

```css
dialog#dlg-card img { max-width: 100%; max-height: 60dvh; object-fit: contain; }
button, a, summary { touch-action: manipulation; }
```

手動確認 12 に「結果画面と武将詳細ダイアログを 360×640 で開き、閉じるボタンに届くこと」を追加する。

### 8. [NIT] 「似ている理由」が武将ごとに自然な文章、という要件 §11 を、史実 1 文以外はテンプレートで満たしている

**場所**: B-9、要件 §11

**問題**: 要件は「説明文は武将ごとに自然な文章になるようにしてください」。第 3 版は固定の結び文(bridge)を廃止し、P1 と P3 を軸から機械的に生成する。矛盾はなくなったが、20 人の P1・P3 は軸ラベルと水準語を差し替えただけの同じ文型になる。武将固有なのは P2(史実 1 文)だけ。

**修正案**: 設計変更は必須ではない。余力があれば、武将ごとに軸別の短い言い回しを 1 つずつ持たせる(`reason.flavor: { leadership:'…', … }` の 6 項目。診断用の解釈であることがわかる文末にし、「診断では…」で始める)。P3 は水準語の代わりにこの言い回しを使う。入れない場合は、B-9 に「P1・P3 は共通テンプレート、武将固有の文は P2 のみ。要件 §11 の『武将ごとに自然』は P2 と武将名の差し込みで満たす、と解釈する」と明記する。

### 9. [NIT] 細かい未定義(`setAnswer`、`uid`、Q1 の「前の質問へ」、`reset()` の退避キー)

**場所**: B-4、B-3(`SG.Util.uid`)、B-12(`reset`)

**問題**:

- B-4 が「`answers` が変わる(= `setAnswer`)とき」と書くが、`setAnswer` は他のどこにも定義がない。
- `SG.Util.uid(prefix)` の生成方法が未規定。`Math.random` を使うと、同じ回答で DOM の ID が変わる(結果には影響しないが、「乱数を使わない」という B-2 の記述と見た目が食い違う)。
- Q1 の「前の質問へ」の状態(非表示か、無効か、スタートへ戻るか)が未規定。
- `store.reset()` は「キー削除+メモリ初期化」だが、読込時に退避した `sengoku-personality:v1:stats:corrupt` を消すかが書かれていない。
